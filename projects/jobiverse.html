01 / PROBLEM

직무 정보는 많지만,
“나와 맞는지”는 알기 어렵습니다.

적성검사는 성향을 알려주고 직무 소개는 업무 내용을 설명하지만, 실제로 업무를 해보는 경험과는 떨어져 있습니다. 인턴·현장실습은 직접 경험할 수 있지만 기회와 시간이 제한적이라는 문제에서 출발했습니다.

BEFORE

읽고 고르는 진로 탐색

검사 결과와 직무 설명을 읽고 선택합니다. 성향 점수는 있지만 어떤 상황에서 잘했고 어디서 막혔는지 행동 근거가 부족합니다.

AFTER

해보고 고르는 진로 탐색

상담에서 관심사를 정리하고 추천 직무의 가상 회사에 입장합니다. 사수·동료·고객과 상호작용하고 과제·미니게임을 수행한 기록이 최종 리포트의 근거가 됩니다.

02 / USER JOURNEY

상담부터 리포트까지
한 흐름으로 연결했습니다.

추천 카드에서 끝나는 서비스가 아니라, 추천 → 체험 → 평가 → 리포트가 끊기지 않도록 직무군과 시나리오를 연결했습니다.

03 / DESIGN DECISIONS

기능보다 먼저
데이터 연결 규칙을 정했습니다.

추천 결과와 체험 콘텐츠가 따로 놀면 사용자는 “왜 이 직무를 추천받았고 왜 이 체험을 하는지” 이해하기 어렵습니다. 그래서 연결 단위를 먼저 고정했습니다.

DECISION 01

추천 단위 = 직무군

세부직업 단위로는 체험 시나리오를 1:1 연결하기 어려워 추천 단위를 직무군으로 통일했습니다. 세부직업은 상담과 리포트 근거로 유지했습니다.

DECISION 02

직무군 ↔ 시나리오 1:1

추천 카드에서 바로 체험으로 입장할 수 있도록 직무군과 시나리오를 직접 매핑했습니다. 38개 직무군 중 37개 시나리오를 연결했습니다.

DECISION 03

콘텐츠와 코드를 분리

시나리오·NPC·자료·미니게임·프롬프트·추천 원장을 data/에 분리해 게임 콘텐츠 변경이 백엔드 코드 수정으로 번지는 범위를 줄였습니다.

04 / MY OWNERSHIP

점수를 보여주는 리포트가 아니라,
“왜 이 점수인지” 설명하게 했습니다.

제 역할은 Reporting · Data Pipeline. 체험 결과를 사용자가 납득할 수 있는 결과물로 바꾸고, 추천과 외부 데이터를 연결하며, 데이터 정합성을 CI에서 계속 확인하는 영역을 맡았습니다.

05 / ARCHITECTURE

08 / TAKEAWAYS

이 프로젝트에서
가장 크게 배운 것.

AI 결과보다 데이터 계약이 먼저다.

추천·시나리오·리포트가 같은 직무 기준을 보지 않으면 LLM 품질과 무관하게 서비스 전체가 어긋납니다.

“근거를 보여주는 기능”도 백엔드 문제다.

사용자에게 설명 가능한 결과를 주려면 원천 데이터, 사용자 기록, 평가 결과를 추적 가능한 형태로 연결해야 합니다.

01 / PROBLEM

한 번의 위로가 아니라
상태 변화에 따라 이어지는 흐름으로 설계했습니다.

반려동물과의 이별은 시한부 선고, 장례 준비, 사후 감정, 일상 복귀가 서로 다른 시점에 이어집니다. 그래서 단발성 생성형 AI 위로가 아니라 생전 → 이별/장례 → 사후 회복 → 추억 보관의 서비스 프레임을 만들었습니다.

SCOPE RISK

좋은 아이디어가 많을수록 시연은 흔들립니다.

수의사 웹, 아바타, 능동 알림 등 기능 범위가 계속 커졌고, 짧은 프로젝트 기간 안에 모두 완성하려 하면 핵심 사용자 흐름이 무너질 위험이 있었습니다.

PM DECISION

핵심 시연 플로우 중심으로 재정렬

프로필 → 감정 체크인 → 메시지/TTS → 회복 미션 → 타임라인/리포트를 기준선으로 잡고 팀 우선순위와 완료 기준을 다시 정했습니다.

02 / SERVICE FLOW

사용자의 상태가 바뀌면
서비스가 제공하는 것도 달라집니다.

감정 체크인과 회복 상태를 중심으로 콘텐츠가 순차적으로 열리도록 설계해, 모든 추모 콘텐츠를 처음부터 한꺼번에 노출하지 않았습니다.

03 / PRODUCT DECISIONS

팀장 역할은
기능을 더하는 것보다 빼는 일이 많았습니다.

18일 안에 발표 날 실제로 연결되어 동작하는 흐름을 기준으로 기능 범위와 우선순위를 줄였습니다.

DECISION 01

서비스 프레임을 시간축으로 통일

각자 구현하는 기능을 생전 준비·이별/장례·사후 회복·추억 보관의 네 단계에 배치해 기능의 목적과 우선순위를 맞췄습니다.

DECISION 02

회복 점수 기반 콘텐츠 해금

GIF → 3인칭 편지 → 1인칭 편지 → 전체 패키지 순으로 단계별 콘텐츠 해금 흐름을 두어 서비스 상태를 백엔드에서 관리했습니다.

DECISION 03

외부 AI는 폴백 전제로 통합

TTS와 멀티모달 기능은 외부 API·GPU 서버 실패 가능성이 있어 여러 폴백을 두고 핵심 API 흐름이 끊기지 않도록 연결했습니다.

04 / MY OWNERSHIP

팀 전체의 기능을
하나의 사용자 흐름으로 묶었습니다.

Team Lead · PM · Backend로 우선순위를 정하고 FastAPI API, 데이터 저장소, 회복 로직, 배포 환경, 최종 시연 흐름을 연결했습니다.

05 / ARCHITECTURE

모바일 앱에서
AI·DB·GPU 서버까지.

React Native 앱 요청은 NCP nginx를 거쳐 FastAPI로 들어오고, 기능에 따라 데이터베이스·Gemini/TTS·RAG·GPU 서버로 분기됩니다.

08 / TAKEAWAYS

이 프로젝트에서
가장 크게 배운 것.

통합은 마지막 단계가 아니다.

각자 만든 기능을 끝에 합치면 실패 지점을 찾기 어렵습니다. 매일 핵심 사용자 흐름을 기준으로 연결 상태를 확인하는 게 중요했습니다.

팀장의 산출물은 의사결정이다.

무엇을 만들지뿐 아니라 무엇을 이번 시연에서 빼고, 어떤 실패를 허용하지 않을지 정하는 일이 개발 속도와 완성도를 크게 바꿨습니다.
